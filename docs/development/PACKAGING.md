# Explicit package inputs

`packaging/manifest.json` defines exact source-relative files for four components.
It is an input allowlist, not a claim that archives have been released or every
native analyzer can run offline. The read-only stdlib tool
`tools/package_manifest.py` validates it and returns sorted path/size/SHA256
records. No directory globs expand at inventory time. Adding a file requires a
reviewed manifest change, plus matching build metadata for core modules.

| Component | Contents and boundary |
| --- | --- |
| core-wheel | Explicit DevSift Python modules, no external runtime dependencies; generated wheel metadata is separate |
| core-sdist | Those Python sources, pinned build configuration, manifest/audit tool and this document; generated sdist metadata is separate |
| consumer-skill | Host-installed SKILL.md, linked CONSUMER-SCOPE.md and explicit offline consumer references; not installed by pip |
| source-assets | DevSift-owned native helper source/project/lock/config inputs, current schema/policy files, trusted setup source and native usage docs; no compiled tools or third-party dependencies |

The Python runtime embeds the canonical policy/registry in its modules. Current
runtime resource inspection found no required package-relative schema/policy
files; explicit user policy paths are caller inputs, not installed defaults.
Schemas/policy files remain their existing source assets, with no copied truth.
The TypeScript factory's default helper path requires a separate trusted source
checkout/setup; its absence in a core install is unavailable, not native coverage.

`pyproject.toml` names each Python module explicitly, disables package discovery
and package data, and pins setuptools 83.0.0. There is no custom build hook.
The package version is 0.1.13 and dependencies remain empty. Exact
`MANIFEST.in` entries bound the core sdist. Wheel/sdist metadata and installer
entrypoints are generated by the pinned backend; source assets and the skill
are separate components. No license decision, tag, publication or release is
implied. The empty license-files list prevents automatic inclusion of unrelated
local license files and does not grant licensing rights. Owner approval of a
license remains a release prerequisite.

## Read-only inventory

From a trusted DevSift checkout run:

```text
python -B tools/package_manifest.py --component core-wheel
python -B tools/package_manifest.py --component consumer-skill
```

The default requires every selected file and the manifest itself to be tracked
in Git, with regular stage-zero index entries. An untracked file occupying an
allowed optional name fails rather than silently joining an artifact. Hashes
represent current physical bytes (including line endings), not a claim of HEAD
byte equivalence. Actual source revision and these hashes must be bound by the
caller before archiving. Inventory is not a secret detector: modifying an
allowed tracked source still needs human review; arbitrary working trees are
not trusted build sources.

All manifest components are parsed/validated before selection. Duplicate keys,
unknown fields/components, unsorted/duplicate or case-colliding paths, absolute,
drive/backslash/dot traversal, symlink/junction/reparse components, special
files and missing required files fail closed. Selected inputs are bounded to
8 MB per file; manifest JSON to 200 KB. Public errors are fixed and do not echo
paths or file contents. No directory-wide scan, native execution, install,
network, source build or target configuration hook runs during inventory.
Git inspection reads only explicit index entries and disables fsmonitor hooks.
The source filesystem and trusted manifest must remain stable during inspection;
this is not an OS sandbox against concurrent hostile filesystem mutation.

For an independently reviewed extracted core sdist without Git, a caller can
explicitly use `--reviewed-extracted-source`. It disables only tracked-index
proof and does not establish provenance; verify the archive and expected hashes
before opting in. Components absent from that minimal sdist remain unavailable.
Unknown/unavailable analysis still returns incomplete through normal runtime
contracts; packaging never upgrades it to a pass.

## Trusted builds and subsequent work

Build only from an explicitly trusted temporary source copy prepared from the
accepted inventory, outside the consumer project. Provision the pinned backend
before any offline build; Python/build tools are external prerequisites. For
example, with setuptools 83.0.0 already installed in the selected environment,
`setuptools.build_meta.build_wheel` and `build_sdist` can operate without network
in that copy. Do not run build commands as part of a scan or on a target project.
Only the setup stage may build DevSift's own helpers or install locked external
dependencies. A core wheel alone has no prebundled native toolchain, Roslyn,
ScriptDom, npm/node_modules, third-party binaries or offline analyzer guarantee.

With `DEVSIFT_TEST_PACKAGE=1`, tests require the exact preinstalled build
backend and build actual wheel/sdist from controlled temporary trusted copies and
inspect member bytes/names, including hostile untracked extra modules, secrets,
maintainer assets and caches. They also exercise manifest/index/path/symlink
boundaries and check that original source/Git state is unchanged. They do not
publish artifacts, certify a license, establish reproducible wheel bytes or
complete install/rollback validation. The default suite runs stdlib inventory
guards and visibly skips the explicit build group; opting in without the exact
backend fails rather than silently skipping. Deterministic source-component
archives are described below; the separately gated installation/rollback group
is documented after the source-bundle contract.

Build pin reference: [official setuptools 83.0.0 release](https://pypi.org/project/setuptools/83.0.0/).


## Reproducible source-component bundles

`tools/build_package.py` implements deterministic ZIP **source input bundles**,
not backend-generated wheels, Python sdists or precompiled native distributions.
The `core-wheel` component becomes `devsift-core-wheel-source.zip`, and
`core-sdist` becomes `devsift-core-sdist-source.zip`. The other names are
`devsift-consumer-skill.zip` and `devsift-source-assets.zip`. A source ZIP is not
a directly installable wheel or an assurance that native analysis is available.
No build backend, compiler, download, dependency installer or publisher runs.
The package version and absence of an owner-selected license are unchanged.

```text
python -B tools/build_package.py build --root <trusted-checkout> --source-sha <full-commit-sha> --output <new-absolute-directory>
python -B tools/build_package.py verify --output <directory> --source-sha <independently-trusted-commit-sha> --integrity-sha256 <independently-trusted-integrity-digest>
```

With no `--component`, all four components are bundled. Repeat `--component`
to select distinct components. The library API is
`build_package(root, destination, source_sha=..., components=(...))`, returning
frozen `Artifact(name, size, sha256)` records. Its only writes are in the new
explicit destination. The matching read-only `verify_bundle(destination,
expected_integrity_sha256=..., expected_source_sha=...)` returns those records
only after every integrity check succeeds. Failures have a fixed public message
and CLI exit 2 without source/config/error-output echoes.

The full lowercase nonzero 40-character Git commit SHA must equal HEAD. The
manifest and every selected path must have matching regular stage-zero index
and commit tree entries. Raw commit blobs are compared with bounded physical
working bytes and the accepted inventory hashes. Changed selected source,
staged changes (even if working bytes were restored), missing files or a changed
manifest fail before output creation. The builder uses raw blob/index queries,
no clean/smudge/process filters, textconv, target hooks or fsmonitor callbacks;
replacement Git objects and inherited Git override variables are disabled.
Unselected files and unrelated untracked secrets never enter these bundles.
This is selected-input cleanliness, not a claim that an entire developer working
tree has no unrelated edits. A commit SHA identifies input objects; it does not
authenticate a remote repository, author, review or publication authority.

Physical CRLF conversion that differs from the commit is rejected rather than
silently attributed to that commit. Prepare an explicitly trusted checkout with
matching bytes (for example disable automatic checkout conversion during setup).
The builder never changes checkout settings or normalizes the user's files.
Different timestamps/host metadata do not affect ZIP bytes: entries are sorted,
stored without compression, fixed at 1980-01-01 00:00:00 with Unix regular-file
0644 metadata, and have no directory, extra or comment entries. There is no
build timestamp, local path or host identity in the integrity record.

`integrity.json` binds the source SHA, exact packaging-manifest SHA256 and each
component archive name, byte size, SHA256 and member path/size/SHA256.
`SHA256SUMS` covers all archives and integrity.json in sorted order; it cannot
hash itself. The JSON is canonical ASCII with sorted keys, compact separators
and a final LF. Archive bytes and these files repeat for the same immutable
inputs and format implementation. This does not establish reproducible wheel,
compiler output or third-party runtime bytes.

Checksums supplied beside an untrusted archive are not authentication. The
verifier requires the expected integrity digest and source SHA independently,
checks archive hashes, exact bounded file lists/content, normalized ZIP metadata,
checksum-file bytes and absence of extra output files. It never extracts or
executes content. Installation needs separately trusted instructions and the
later install/rollback checks; do not derive a new trusted digest merely to
accept changed content.

The output must be an absolute, nonexistent directory outside source and its
actual Git/common directories, with existing ordinary parent directories.
Existing files/directories and symlink/junction/reparse components are rejected.
Inputs are fully checked before creating the destination, then files are opened
exclusively. An OS write failure may leave a partial new directory, which is not
a valid bundle and is never silently reused or overwritten. Source and output
parents must remain under trusted stable control; these checks are not an OS
sandbox against a concurrent hostile filesystem owner. Source data is bounded
to 8 MB per file and 64 MB of distinct inputs; manifest and integrity parsing
are bounded. No output is created inside a consumer checkout as part of a scan.

`python -B -m unittest discover -s tests -p test_build_package.py -v` uses real
temporary Git commits, repeated ZIP builds, trusted-digest verification,
tampering, selected dirty/staged/missing inputs, wrong commit IDs, no-overwrite,
source/Git output boundaries and actual source/output symlink cases. Source
file/directory hashes and Git state remain unchanged by build/verify. These
are local source-bundle results, not hosted cross-platform release or signing
proof. Publication remains separate; the actual fresh install/rollback checks
below provide a different artifact-installation proof.

Archive source proof rejects effective partial/promisor configuration and shallow
history before object lookup. Git calls explicitly disable lazy fetching and use
accepted host Git selection outside the selected source root. The builder reads
physical manifest inputs, then independently proves exact stage-0 index/commit
membership; the inventory extraction opt-out alone is never provenance.

## Actual offline installation and explicit rollback

Provision `setuptools==83.0.0` in the selected trusted test interpreter during an
explicit setup step. Then set `DEVSIFT_TEST_PACKAGE_INSTALL=1` using your shell's
syntax and run:

```text
python -B -m unittest discover -s tests -p test_package_install.py -v
```

Opting in without the exact backend fails; it never skips for missing tools or
downloads setup dependencies during the test. The existing installed-CLI workflow
sets this opt-in mandatorily on both Windows and Linux after explicit backend
setup and a full-history checkout. That workflow configuration is not itself
evidence of a hosted result. The default local suite visibly skips this group.

The test reads the selected HEAD's raw regular-file commit blobs, after rejecting
effective partial/promisor and shallow history. It uses hardened host Git with
lazy-fetch/replacement/fsmonitor/optional-lock guards, bounds object sizes before
reading and prepares only the manifest's explicit inputs in a temporary stage.
It never normalizes the primary checkout, clones a workspace or rewrites source
to overcome Windows CRLF differences. The accepted original source commit and
the temporary stage's new fixture commit are distinct identities: the latter
proves selected physical stage bytes for the source-bundle builder, while module
content is compared against the original commit's extracted bytes.

The provisioned backend builds an actual wheel and Python sdist in that trusted
stage. Wheel metadata/entrypoint and RECORD hashes are inspected; all 42 runtime
module files must match expected commit bytes. Every sdist member is checked for
bounded regular-file/directory type, root prefix and traversal/link exclusions
before its contents are copied individually into a new temporary directory.
There is no unrestricted `extractall`. The sdist's 42 module payloads must match,
then the verified trusted sdist is rebuilt offline into another actual wheel.
Installing that wheel proves the supported sdist-to-wheel-to-install path, not a
claim that a ZIP source bundle is directly installable.

Disposable virtual environments use their bundled pip and local wheel files with
`--no-index --no-deps --no-compile --force-reinstall`. No global environment is
installed into. Each install checks the installed distribution's module inventory,
raw module hashes and RECORD entries, imports the modules (the executable
`__main__` is exercised through `-m`), and runs actual isolated
`devsift scan --all --security` plus the console entrypoint. The
consumer fixture contains target-package/build-hook traps; those files are
inspected only as source data, never imported, built or executed. Consumer/Git
file bytes, selected original checkout bytes, its index and HEAD remain unchanged.

Rollback uses an **explicit synthetic prior-artifact fixture**, not a historical
release or a new project version. Its initializer has a harmless distinct comment
and its wheel omits the otherwise independent `verification_plan.py` leaf module.
The test audits both trusted artifacts and captures their expected digests before
installation. It installs prior → current → explicitly selected prior with pip
force-reinstall, checking each hash set and working CLI. After rollback, the prior
initializer is restored and the current-only leaf file is physically absent and
removed from installed RECORD inventory. This proves tested pip replacement and
removal behavior; it does not automatically choose, authenticate or authorize a
rollback for a consumer installation.

The accepted source-bundle API is also exercised separately with independently
held expected integrity digest and fixture source SHA. Its consumer-skill archive
contains exactly `SKILL.md` and its linked `CONSUMER-SCOPE.md`; verification reads
those bytes without extraction or host activation. Source-assets members match
the explicit allowlist and contain no native executables/libraries or wheel.
This establishes bundle integrity for the tested inputs, not native availability,
agent-host obedience or automatic skill installation. Wheel/native byte
reproducibility, signatures, publication, legal license selection and release
authorization remain separate and are not claimed by these tests.
